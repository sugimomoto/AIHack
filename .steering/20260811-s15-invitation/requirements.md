## 1. 目的

> **一方が相手を招待でき、相手が参加していなくても一人で使える状態にする。**

### 1.1 これは C2 の実装本体である

product-requirements.md はこう主張している。

> **C2. 入口を協議離婚に置く**
> 協議離婚と公正証書作成は制度上、双方の関与が前提である。したがって入口を前段に置くことで、
> **「相手を招待できない」という獲得上の障壁が構造的に解消される。**

**この「解消される」を実現する機能が、これまで存在しなかった。**中核コンセプトの1つが主張だけの状態だった。

### 1.2 核心の問い

**招待という行為そのものが、相手を刺激しうる。**

ユーザーは「相手と関わりたくない」層である（→ 国の調査で取り決めをしない理由の第1位）。
**元配偶者からアプリの招待が届くこと自体**が引き金になりうる。

## 5. 設計上の要点

### 5.1 招待メールは「通常のメールより安全な経路」になる

| 制約 | 帰結 |
| --- | --- |
| 当事者が自由文を書けない | **この経路で罵倒や脅迫を送れない** |
| 件名・本文から内容が推測されない | 相手の職場・家庭で見られても危険が小さい |
| 再送しない | 催促による圧迫がない |

> **制約が安全性に転じている。**この点は設計の主張として明記する。

### 5.2 準備モードは新エンティティを作らない

```
Proposal.status = DRAFT     ← 相手がいないあいだ
        ↓ 相手が参加
Proposal.status = PENDING   ← 提案として提示される
```

変換処理が不要であり、参加後にそのまま提案になる。

### 5.3 年収は `Party` に保存しない

```
入力: 4,380,000円
  ├→ ContactInfo.annualIncome  （SELF_ONLY・ケース配下に置かない）
  └→ Party.incomeBand = "400-425"  （★これだけが越える）
```

**`Party` に精密な年収を保存した時点で INV-2a が破れる。**
