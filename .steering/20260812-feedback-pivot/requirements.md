# 要求：取り決めは「入力」で作る。AI に触らせない

- 作成日：2026-08-12
- 起点：実体験者へのヒアリング
- 議事の原本：`.meetings/`（**Git 対象外・実名を含む**）。本書は匿名化済み

---

## 1. 方針

> **「取り決め」画面は、公正証書に入れる内容を管理する場所とする。**

| | 誰が作るか | 公正証書 |
| --- | --- | --- |
| **取り決め** | **ウィザードと編集画面だけ。AI は触らない** | **載る** |
| 相談（対話） | AI が仲介する。**取り決めは動かさない** | 載らない |

### 1.1 ★ 決めたこと

1. **AI との対話で取り決めを決定・変更する機能をやめる**
2. 設定は**入力ウィザードと編集画面**に限る
3. **AI にこの編集をさせない**
4. **財産分与・年金分割**をウィザードの対象に**加える**
5. **慰謝料は対象外**
6. **取り決めの入力は「取り決め」画面で行う。**オンボーディングでは聞かない
7. **オンボーディングを、次の3つだけにする**
   - アプリの説明（メッセージを転送しないこと）
   - サインアップ（次に使うときのためのメール登録）
   - **お相手の招待を、いま行うかどうか**
8. 算定表は**範囲だけ**を出す。**差についての説明文はやめる**（AI を金額から完全に外す）
9. 財産分与・年金分割の条項は、**協議したことを記す最小の形**にする

### 1.2 なぜこれで良くなるか

いまの実装は、対話から抽出した値で取り決めを作っている。そこから出た問題：

- **「進学費用の分担」の話が、合意済みの養育費の月額を書き換えうる状態だった**
  （実測。`kind` で歯止めを入れたが、**歯止めが要ること自体が構造の問題**）
- 抽出が品目を言い換え、**スマホ代がコピー代に化けた**（実測）
- はっきり書いた人ほど、逐語一致で**伝わる中身が減っていた**（実測）

**取り決めを入力に限れば、これらは構造的に起こらない。**
P3（数字と条項を LLM に作らせない）も、例外なく守られる。

### 1.3 失うもの・失わないもの

| | |
| --- | --- |
| **失う** | 「対話しているうちに取り決めができあがる」体験 |
| **失わない** | 算定表の目安（**LLM を通していない**）。相談の仲介。臨時費用の相談。変更の申し出（K-6 はフォーム） |

## 2. 今回の要求

### 2.0 ★ オンボーディングを削ぐ

いまは 状況の5択 → 同居 → お子さん → 年収 を通り道で聞いている。**これをやめる。**

| いま | これから |
| --- | --- |
| I-1 状況の確認（5択） | **やめる**（全員が入力から始まるので、分岐する意味が無くなる） |
| I-2 同居 | **取り決め画面へ**（養育費を入れるときに、受け取る側を決めるために聞く） |
| I-3 お子さん | **取り決め画面へ**（算定表に要る） |
| I-4 年収 | **取り決め画面へ**（算定表に要る） |
| I-6 メールの登録 | **残す** |
| 招待 | **オンボーディングに戻す**（いま行うかどうかを尋ねる） |

> ★ 第3弾の設計は「招待をオンボーディングから外す」と決めていた。
> 理由は「聞いた時点で、アプリが相手に伝える前提でいることが伝わる」。
> **今回それを戻す。**ただし当時の懸念は残るので、次を守る：
> - 関係の状態（話しているか等）は**一切聞かない**
> - 「あとにする」を**同じ重さ**で置く
> - 渡すまで相手には何も届かないことを、その場に書く

### 2.1 スコープ

1. **取り決めのウィザードと編集画面**（対話を経ずに作れる／直せる）
   - 養育費：金額・支払日・終期
   - **面会交流**：回数・曜日・週・時間・受け渡し場所
   - **財産分与**（新規）
   - **年金分割**（新規）
2. **対話から取り決めへの経路を断つ**（提案を作らない）
3. 入力したものが、これまでと同じ扱いになること
   （合意の判定／予定／公正証書の原案／変更の申し出）
4. **オンボーディングの簡素化**（2.0）
5. **必要な情報は、必要になった時点で聞く**
   （養育費を入れようとしたときに、お子さん・年収・同居をその場で）

### 2.2 スコープ外

| | 理由 |
| --- | --- |
| **慰謝料** | 対象外と決定 |
| 離婚への同意・親権者・婚姻費用 | 扱える設計になっていない。**扱えないものを出さない** |
| 臨時費用を独立した単位にする | → Issue #7 |
| 領収書などの画像 | → Issue #6 |
| 面会の実施記録 | → Issue #5 |
| 口座連携による入金確認 | **「入金を観測できない」という不変条件を捨てることになる** |

## 3. ユーザーストーリー

### US-1（これから決める人）

> 何を決めればよいのかが分からない。対話で一つずつ引き出されるより、
> **決めるべき項目が並んでいて、埋められるところから埋めたい。**

### US-2（すでに決めてある人）

> 公正証書は作ってある。その内容を入れておけば、予定や履行の記録に使える。
> 養育費だけでなく**面会のルールや財産分与も入れたい。**

### US-3（対話から入りたい人）

> フォームを見せられると身構える。思っていることから書き始めたい。

> ★ US-3 を壊さない。**相談は残る。**ただし相談は取り決めを動かさない。

### US-4（決めたことを直したい人）

> 金額を直したい。**相手の同意が要ることは分かっている。**
> 対話で言うのではなく、**その項目の画面から申し出たい。**

## 4. 受け入れ条件

- [ ] **AC-1**：対話を一度も使わずに、4つの論点すべてを取り決めにできる
- [ ] **AC-2**：★**対話からは取り決めが作られない・変わらない**（提案が生成されない）
- [ ] **AC-3'**：「これから」には、**相談から決まったことだけ**が並ぶ
- [ ] **AC-3''**：★**履行の申告・逸脱の検知・リマインドを画面に出さない**
      （手間で押されず、押されないと**事実でない疑い**が立つため。→ `design-upcoming.md`）
- [ ] **AC-4**：取り決めが公正証書の原案に載る（4論点それぞれに条項ひな形がある）
- [ ] **AC-5**：取り決めを画面から直せる。**直すには相手の同意が要る**（K-6）
- [ ] **AC-6**：入力は**飛ばせる**。飛ばしても行き止まりにならない
- [ ] **AC-7**：片方が入力しただけでは合意にならない
      （記録として残り、相手が同じ内容を記録したときに合意になる）
- [ ] **AC-8**：書かれていない項目を、こちらで埋めない
- [ ] **AC-9**：相談（対話）は従来どおり動く。取次ぎも臨時費用の相談も残る
- [ ] **AC-10**：オンボーディングは3つだけ（説明・サインアップ・招待するか）
- [ ] **AC-11**：★**算定表は範囲だけを出す。**差についての説明文を出さない
- [ ] **AC-12**：算定表に要る情報（お子さん・年収）は、**養育費を入れる場面で**聞く

## 5. 制約

### 5.1 壊してはいけない不変条件

| # | 内容 |
| --- | --- |
| **P3** | 数字と条項を LLM に作らせない。**今回これが例外なく守られる形になる** |
| **合意の成立** | 双方が承諾し、**かつ内容が一致**したときだけ確定 |
| **G-3 / G-3b** | 条項に出せるのは、表記の定義がある値だけ |
| **C1** | 入力した内容も、そのままは相手に渡らない。合意した事項だけが共有される |
| **A-1 / INV-1** | 他人のケースは触れない |

### 5.2 新しい論点を足すときの規律

財産分与・年金分割を足すことは、**新しい条項を書くこと**を意味する。

- **条項ひな形と payload スキーマは1対1**（G-3）。ひな形の無いスキーマを公開しない
- **LLM に条項を書かせない。**ひな形は人が書く
- 法的な文面は**断定しない**。原案であることの注記を外さない
- ★**年金分割は、按分割合や情報通知書など手続きが特殊。**
  扱いを誤ると当事者の手続きを誤らせる。**一次資料での確認が要る**

### 5.3 時間

締切 2026-08-15 15:00。提出物は「完全版」ではなく、
**コンセプトと体験価値が伝わるデモと説明資料**。
