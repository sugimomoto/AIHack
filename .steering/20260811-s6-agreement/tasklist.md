## ★ 実機で重大な欠陥を検出した

**双方が承諾すれば合意になる、という実装は誤りだった。**

```
Aの提案 3万円 ／ Bの提案 4万円
双方が「この内容で進める」を押す
  ↓
monthlyAmount: 30000 が合意として記録された
```

**誰も合意していない金額が確定した。**

### なぜ起きたか

`canFinalize` が承諾の有無だけを見ていた。
`payload` は `reduce` で合成していたため、**後勝ちで片方の提案が採用された。**

### なぜ合成してはいけないか

**何に承諾したのかが定まっていなければ、承諾は意味を持たない。**

そして P3 により、**AIが中間の金額を決めることもできない。**
「3万と4万だから3万5千」は、AIが金額を作ることである。

> **一致は当事者が作るしかない。**

### 直した内容

```
確定できる条件 ＝ 双方が承諾 かつ 提案が一致
```

一致していないときは `NEEDS_CONVERGENCE` とし、**承諾ボタンを出さない。**

```
おふたりのご提案の内容が異なっています。
同じ内容になったときに、お進みいただけます。
```

**項目が欠けていても一致とみなさない。**
「支払日は決めていない」状態を合意にすると、後で解釈が割れる。

## ★ 算定表のデータは未検証である（R-18）

一次資料からの正確なデータ化ができていない。

```
❌ それらしい数字を、算定表の値として提示する
     → このプロダクトが防ごうとしている害を、自分で起こす。
       当事者は「裁判所の基準」として受け取る。

✅ 未検証であることを、出力から外せない形にする
```

### 外せない形にした

| 手段 | 内容 |
| --- | --- |
| **注記を参照結果に含める** | `lookupChildSupport` が `caveat` を返す。<br>呼び出し側が付けるのではない。**任せると、いつか忘れる** |
| **`formatRange` は引数を1つしか取らない** | 「注記を出さない」選択肢を呼び出し側に与えない |
| **テストで固定** | 未検証の表を使った出力に注記が無ければ落ちる |

実際の出力：

```
算定表（表1（子1人・0〜14歳））では、この年収帯は月2万〜4万円の範囲とされています。
※この金額は未検証のサンプル値です。裁判所が公表する算定表と照合していません。
　実際の取り決めには、必ず一次資料をご確認ください。
```

**LLM が生成した説明文にも、この注記がそのまま含まれた。**
