## 1. 目的

**実装前に、弁護士と共同養育の当事者にしか判断できないことを潰す。**

本プロジェクトの差別化は「法律家 × IT × 当事者」の3者体制にある（→ product-requirements.md §5.6）。しかし**二人はまだ設計を見ていない。**

| 誰 | その人にしか判断できないこと |
| --- | --- |
| **共同養育の当事者** | 文言に耐えられるか。呼称は適切か。**感情が高ぶっているときにこの画面を開けるか** |
| **離婚案件を専門とする弁護士** | 8論点の表現が実務に合うか。**非弁の観点で危ういUIがないか**。法的説明に誤りがないか |

**実装後に「この文言は当事者を傷つける」と指摘されたら作り直しになる。**モックの段階なら文言の変更で済む。

### 1.1 これは何ではないか

| | |
| --- | --- |
| ❌ 動作するプロダクト | バックエンドを持たない。AIも動かない |
| ❌ 使い勝手の検証 | ユーザビリティテストではない |
| ✅ **体験と文言のすり合わせ** | 「これで伝わるか」「これは言っていいのか」を確認する |

---

## 2. ★ 最重要要件：視点の切り替え

**父と母、両方の画面を切り替えて見られること。**

本プロダクトの主張は「**あなたが書いた言葉は、相手に届いていない**」である。**片側だけを見せても検証にならない。**同じ場面を両側から見て初めて、封書カード（③取次ぎ）の意味が伝わる。

```
   父の視点                        母の視点
┌──────────────┐              ┌──────────────┐
│「また勝手に土曜│   ⟷ 切替     │ ✉ お相手からの│
│ に決めやがって」│              │   ご相談      │
│              │              │ 土曜の日程に  │
│ ここに書いた   │              │ ついて、別案の│
│ ことは、お相手 │              │ ご相談が来て  │
│ には届きません │              │ います        │
└──────────────┘              └──────────────┘
```

| 要件 |
| --- |
| 画面上部などから**いつでも視点を切り替えられる** |
| 切り替えても**会話の時点（シーン）は保たれる** |
| 「いま誰の画面を見ているか」が常に分かる |

> **この切替がないと、モックを作る意味が半減する。**

## 3. 実装方針

### 3.1 捨て実装にしない

| 方針 | 内容 |
| --- | --- |
| フレームワーク | **Next.js（App Router）＋ TypeScript ＋ Tailwind CSS**（本実装と同じ） |
| データ | **ハードコード**（`src/mock/scenario.ts` 等に集約） |
| バックエンド | **なし。**Firestore も LLM も呼ばない |
| コンポーネント | **本実装の構造で作る**（`OwnMessage` / `AiMessage` / `RelayMessage` 等） |

> **S4以降で「データ源を差し替えるだけ」になる状態を目指す。**モックのために別構造で作らない。

### 3.2 デザイントークンを先に入れる

配色・タイポグラフィ・余白・角丸を CSS 変数として定義する（→ design/README.md の Design Tokens）。**これは本実装でそのまま使う。**

### 3.3 デプロイ

**インフラ（S0）の完成を待たない。**二人に見てもらうことが最優先。

| 状況 | 手段 |
| --- | --- |
| GCP が未整備 | 静的ホスティング（Vercel 等）で先に共有する |
| S0 完了後 | Cloud Run へ移す。**モックのデプロイが S0 の疎通確認を兼ねる** |

## 4. スコープ

### 4.1 実装する画面

デザイン納品の**高精度4画面**を優先する。

| # | 画面 | 目的 |
| --- | --- | --- |
| 1 | **ホーム** | 「開いても何もしなくていい」が伝わるか |
| 2 | **相談（対話）** | **3種別の描き分けが伝わるか**（最重要） |
| 3 | **相談の開始（トピック選択）** | 4分類が実際の話題を覆えているか |
| 4 | **「今回だけ／今後も」の確認** | 二択の重さの違いが伝わるか。文言が法的に正確か |
| 5 | **取り決め（合意一覧）** | 8論点の表現が実務に合うか |

### 4.2 実装しない

| 除外 | 理由 |
| --- | --- |
| 公正証書の原案・これから・逸脱の詳細・設定 | 納品が**ラフ**。すり合わせの主眼ではない |
| 実際の対話（AI応答の生成） | シナリオを固定で進める |
| 認証・招待 | 視点切替で代替 |
| データの永続化 | 不要 |
| ダークモード | 対象外（→ ui-design.md §6.1） |

### 4.3 進行方式

**シナリオを固定し、進める／戻せるようにする。**自由入力は受け付けるが、応答は台本どおりに返す。

```
① ホーム（取次ぎが1件ある状態）
② 相談を開く → 封書カードを読む
③ 感情的な文面を入力する
④ 「ここに書いたことは、お相手には届きません」が出る
⑤ AIが受け止める
⑥ ★視点を母に切り替える → 何が届いたかを見る
⑦ 母が「日曜でいい」と答える
⑧ ★父に戻す → 「今回だけ／今後も」を聞かれる
⑨ 取り決め一覧が更新される
```

**⑥が本モックの山場。**

## 6. ⚠️ モックであることを明示する

**完成度が高いと「もう動く」と誤解される。**特に弁護士に対しては、**動作しないものを動作するかのように見せない**ことが信頼上重要である。

| 対応 |
| --- |
| 画面のどこかに常時「**これはデザインの確認用のモックです。実際には動作しません**」を表示する |
| AI の応答は**あらかじめ用意した文章**であることを明記する |
| 公正証書の原案は表示しない（誤解の余地が最も大きい） |
