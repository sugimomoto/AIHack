## 1. 目的

> **養育費が合意できる。**

### 1.1 ★ ここで初めて「数字」を扱う

S5 までは、越えるのは**言葉と構造**だけだった。
S6 は**金額**を扱う。そして金額は、間違うと当事者の生活に直接影響する。

```
P3｜数字と条項はLLMに作らせない
  金額は算定表の決定的な参照で出す。
  LLMは説明と対話のみ担当する。
```

### 1.2 ★ 算定表のデータが未検証である（R-18）

裁判所が公表する養育費算定表を、**一次資料から正確にデータ化できていない。**

```
❌ それらしい数字を入れて、算定表の値として提示する
     → このプロダクトが防ごうとしている害を、自分で起こす。
       当事者は「裁判所の基準」として受け取る。

✅ 未検証であることを、出力から外せない形にする
     → 検査で担保する。注記を消せないようにする。
```

**「動くデモ」のために数字の正しさを曲げない。**

## 3. ★ テストを先に書く対象

| 対象 | 理由 |
| --- | --- |
| **算定表の参照が決定的であること** | LLM が入り込む余地がないこと |

## 5. 設計上の要点

### 5.1 算定表はマスタである（G-1〜G-4）

コードに埋め込まない。DB に置き、版を持つ。
**一次資料から正しくデータ化できた時点で、コードを変えずに差し替えられる。**

### 5.2 `verified` フラグ

```ts
type SupportTableMaster = {
  verified: boolean        // ★一次資料と照合済みか
  sourceNote: string       // 出典・照合状況
}
```

`verified: false` のとき、**参照結果に注記が必ず付く。**
注記は呼び出し側が付けるのではなく、**参照関数が返す値に含める。**
呼び出し側に任せると、いつか忘れる。

### 5.3 調停案は説明だけを生成する

```
入力に渡すもの: 算定表から取得済みのレンジ、双方の payload
生成させるもの: **説明の文章のみ**
```

### 5.4 双方の承諾

片方の承諾では `AGREED` にしない。**合意とは双方の意思の一致である。**
