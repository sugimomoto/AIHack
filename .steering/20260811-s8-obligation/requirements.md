## 1. 目的

> **約束が予定として見え、履行が記録される。**

### 1.1 ★ ここで扱うのは「決まったこと」だけである

予定は**合意から導く。**当事者が別々に入力するものではない。
そうしないと、予定そのものが新しい争点になる。

```
AgreementItem（AGREED）→ Obligation（期日・金額）→ Fulfillment（履行の記録）
                          ↑ 決定的に生成する
```

### 1.2 ★ 語彙が最も難しいスライスである

「支払われていない」という状態を、**責める語彙なしに**表現しなければならない。

| 使わない | 使う |
| --- | --- |
| 未払い | **入金が確認できていません** |
| 違反 | 逸脱 |
| 滞納・遅延 | （使わない） |

**振込の反映遅れがありうる。**断定した瞬間に、事実でないことを相手に伝える可能性が生まれる。

## 2. スコープ

### 2.1 実装する

| # | 項目 |
| --- | --- |
| 1 | **`Obligation` の生成**（合意から決定的に。LLM不使用） |
| 2 | 支払日コード → 実際の日付（月末・31日の無い月の扱い） |
| 3 | **`Fulfillment` の記録**（自己申告） |
| 4 | **双方の申告が揃ったときのみ「確認済み」** |
| 5 | 予定画面 |
| 6 | **リマインダー（★自分にだけ。相手に送らない）** |

### 2.2 実装しない

| 除外 | 理由 |
| --- | --- |
| 逸脱検知・通知 | **S9** |
| 先取特権の判定 | S9 |
| 銀行口座との連携 | 範囲外。**自己申告に留める** |

## 3. ★ テストを先に書く対象

| 対象 | 理由 |
| --- | --- |
| **期日の生成が決定的であること** | 予定が揺れると、それ自体が争点になる |
| **月末・31日の無い月の扱い** | 2月31日という期日を作らない |
| **状態の文言に禁止語が出ないこと** | 責める語彙を相手に届けない |
| **一方の申告だけで「確認済み」にしないこと** | 一致していないことを、一致したことにしない |

## 5. 設計上の要点

### 5.1 「確認できていない」と「支払われていない」は違う

アプリは**入金を観測できない。**観測できないことを断定しない。

```
支払った側が申告      → 「お支払いの記録があります」
受け取った側が申告    → 「入金の記録があります」
双方が申告            → 「確認できました」
どちらも申告なし      → 「まだ記録がありません」   ← ★「未払い」ではない
```

### 5.2 リマインダーは自分にだけ

相手に送ると**催促**になる（U-5）。
予定を思い出すのは、義務を負う本人の仕事である。
