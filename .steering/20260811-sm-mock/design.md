## 1. ★ 設計の核：モックのデータモデル自体が C1 を体現する

視点切替を「2つの画面を用意する」実装にしない。**イベントの列を1本持ち、視点ごとにフィルタする。**

```ts
type Party = 'CUSTODIAL' | 'NON_CUSTODIAL'

type MockEvent =
  | { t: 'own';      party: Party; text: string }              // 自分の発言
  | { t: 'ai';       party: Party; text: string }              // AI自身の発言
  | { t: 'relay';    to: Party; title: string; body: string; hearsay?: string }
  | { t: 'choices';  party: Party; items: string[] }
  | { t: 'sheet';    party: Party; kind: 'scope' }
  | { t: 'agreement'; topic: AgreementTopic; status: AgreementStatus }

// 視点 p のビュー
const viewOf = (events: MockEvent[], p: Party) =>
  events.filter(e => ('party' in e ? e.party === p : 'to' in e ? e.to === p : true))
```

**`own` イベントは `party` が一致する視点にしか現れない。**したがって、
**相手の生の発言は、実装上どうやっても他方の画面に出てこない。**

> **これは見た目の再現ではなく、C1 の構造そのものである。**
> S2 で実装する `buildRelayContext`（`partyId` を引数に取らない）と同じ思想を、モックの段階から持たせる。
> レビューで「本当に届かないのか」と問われたとき、**フィルタ1行を見せて説明できる。**

## 2. シナリオ

固定の9シーン。進める／戻せる。

| # | シーン | 視点 | 見てほしいこと |
| --- | --- | --- | --- |
| ① | ホーム（取次ぎ1件） | 別居親 | 開いても何もしなくていい感じ |
| ② | 相談を開く | 別居親 | **封書カード**（③取次ぎ） |
| ③ | 感情的な文面を入力 | 別居親 | **「ここに書いたことは、お相手には届きません」** |
| ④ | AIが受け止める | 別居親 | responseが説教くさくないか |
| ⑤ | 選択肢が出る | 別居親 | 定型文に見えないか |
| ⑥ | **視点を切り替える** | **同居親** | **★山場。**何が届いたか／届かなかったか |
| ⑦ | 同居親が答える | 同居親 | |
| ⑧ | 別居親に戻る → 確認シート | 別居親 | **「今回だけ／今後も」の重さの違い** |
| ⑨ | 取り決めが更新される | 別居親 | 8論点の表現 |

**⑥が本モックの山場。**ここで「なるほど」と言われなければ、プロダクトの前提が伝わっていない。

## 3. 画面構成

### 3.1 モックのシェル

```
┌─────────────────────────────────────┐
│ これはデザイン確認用のモックです      │ ← 常時表示（AC-M7）
│ 実際には動作しません                 │
├─────────────────────────────────────┤
│                                     │
│         ┌──────────────┐            │
│         │              │            │
│         │  アプリ画面   │            │ ← 390×844
│         │              │            │
│         └──────────────┘            │
│                                     │
├─────────────────────────────────────┤
│ ◀  ③ 感情的な文面を入力  ▶  (3/9)   │
│ 視点: [別居している親] [同居している親]│
└─────────────────────────────────────┘
```

| 要素 | 仕様 |
| --- | --- |
| モック告知 | 上部固定。控えめだが常時見える |
| シーン送り | `◀` `▶` ＋ シーン名 ＋ 進捗（n/9） |
| **視点切替** | **2択のトグル。現在の視点が明確に分かる** |
| 端末フレーム | PC幅のときのみ表示。スマホでは全画面 |

> **視点切替のラベルに「父」「母」を使わない**（→ glossary.md §4）。**「別居している親」「同居している親」**とする。監護親が父であるケースは実在する。

## 7. ★ レビュー依頼書

**本スライスの主成果物。**二人の時間は限られているため、**何を見てほしいかを絞る。**

### 7.1 共通の前置き（両者に送る）

> 離婚・共同養育の当事者が使うスマートフォンアプリのデザインができました。
> **実装前に、お二人にしか判断できないことを確認させてください。**
>
> URL：（後日）
>
> **これは動作しないモックです。**AIの応答はあらかじめ用意した文章で、実際には動きません。
> 画面下の `◀` `▶` で場面を進められます。
>
> **画面の下にある「視点」の切り替えを必ずお試しください。**
> 同じ場面を、別居している親と同居している親の両方から見られます。
> **このアプリの主張は「書いた言葉が相手に届かない」ことなので、両側から見ないと伝わりません。**
>
> お時間は 10〜15分で結構です。以下の問いにだけお答えいただければ十分です。

### 7.2 共同養育の当事者への問い

**7つ。実際に使う人の感覚でしかわからないことに絞る。**

| # | 問い | 見る場面 |
| --- | --- | --- |
| **1** | **感情が高ぶっているとき、この画面を開けますか。**開けないとしたら、何が障害になりますか | 全体 |
| 2 | 相手を「**お相手**」と呼んでいます。耐えられますか。他にどう呼びたいですか | 全体 |
| 3 | 「**ここに書いたことは、お相手には届きません**」——**信じられますか。**不安が残るとしたら何が足りませんか | ③ |
| 4 | 封書のカードを見て、「**これは相手が書いた言葉ではない**」と分かりますか | ②⑥ |
| 5 | AIのキャラクター（カピバラ）は適切ですか。**子どもっぽく感じませんか** | 全体 |
| 6 | 相談の分類は4つです。**実際のやりとりで出てくる話題は、これで足りますか。**足りないものを教えてください | トピック選択 |
| 7 | 「**今回だけですか、今後もですか**」と聞かれるのは自然ですか。うるさく感じませんか | ⑧ |

### 7.3 離婚案件を専門とする弁護士への問い

**7つ。1を最優先とする。**

| # | 問い | 見る場面 |
| --- | --- | --- |
| **1** | **非弁行為の観点で、危うい画面や文言はありませんか。**「法律相談をしている」と受け取られかねない箇所を指摘してください | 全体 |
| 2 | 8つの論点の**並びと名称**は、実務の感覚に合っていますか | 取り決め |
| 3 | 「**取り決め**」という語を使っています。適切ですか（「合意」「協議」等との使い分け） | 取り決め |
| 4 | 「**今後も変更する＝取り決めそのものを書き換えます。お相手の同意が必要です**」——この説明は法的に正確ですか | ⑧ |
| 5 | 養育費の金額は**算定表の範囲を示すだけ**にしています。「〜とされています」という言い方で十分ですか。**踏み込みすぎ／足りない**はありませんか | 対話 |
| 6 | 実際の当事者に見せたとき、**誤解や紛争を生みそうな表現**はありませんか | 全体 |
| 7 | 逸脱時に**先取特権の範囲**（子1人あたり月8万円）を説明する画面を予定しています。**書きすぎでしょうか** | 説明のみ |

> 7は今回のモックに含めない。**文章で説明して意見を聞く。**

### 7.4 答えなくてよいこと（両者に明記する）

**限られた時間を、その人にしか答えられないことに使ってもらう。**

| 対象 | 理由 |
| --- | --- |
| 色や書体の好み | 設計上の意図があり、根拠がある |
| 余白・配置の微調整 | 実装時に詰める |
| 動作の速さ・引っかかり | モックのため実装と無関係 |
| 「もっと機能があったほうがいい」 | 現在は意図的に絞っている |
| 誤字脱字 | ありがたいが優先度は低い |
