# 設計：取り決めは「仮案を作って、了承してもらう」

- 対応する要求：`requirements.md`（AC-7 の作り直し）
- 作成日：2026-08-12（共有の切り替えについての指摘を受けて）

---

## 1. きっかけ

> 取り決めの基本的な条件面は、**どちらか片方が仮案を作って、そこから了承する形**になる。
> なので、**相手に共有するかどうかを、ドラフトした側が ON・OFF 切り替えられる**ようにするのが良いのでは。

---

## 2. ★ この指摘が突いていること

`design.md` §3.2 で書いた状態は、こういう前提でした。

```
双方が独立に記録する → 内容が一致したら合意
```

**これは現実に起きません。**
二人が別々に「月5万円・毎月25日・22歳まで」と打って完全一致することは、まず無い。

> **「内容が異なる」が、例外ではなく標準の状態になっていた。**
> 依頼書で「いちばん難しい画面」として出したものが、実は**通常の画面**になるところだった。

### 2.1 しかも、既知の欠陥の発生条件そのもの

`src/domain/agreement/consent.ts` の冒頭に、実機で見つけた欠陥が記録されている。

```
Aの提案 3万円 ／ Bの提案 4万円 で双方が承諾
→ 誰も合意していない 3万円が確定した
```

`payloadsAgree` はこれを防ぐために入れた**歯止め**である。

**仮案→了承にすると、了承する側は同じ提案に承諾する。**
`payloadsAgree` は自明に真になり、`NEEDS_CONVERGENCE` は**発生条件を失う。**

> ★ 歯止めを増やすのではなく、**条件そのものが消える。**
> `kind` の件（進学費用が養育費を書き換えうる）と同じ形の修正である。

### 2.2 データ層はすでにこの形

| | |
| --- | --- |
| いまの型 | 提案（Proposal）＋ 双方の承諾（Consents） |
| 足りないもの | **「まだ見せていない」という状態だけ** |

**変更は小さい。**

---

## 3. 共有の切り替え

### 3.1 ★ 見ていない状態には戻せない

OFF に戻せるスイッチは、**取り消せるように見える。**

これは「届きません」→「直接届きません」と同じ種類の問題である。
**操作の見た目が、実際にできることより多くを約束してしまう。**

### 3.2 決めたこと

| 操作 | 意味 | 相手に見えるもの |
| --- | --- | --- |
| **既定** | **下書き。自分だけ** | **何も見えない** |
| **ON にする** | お相手に見ていただく | 「お相手が、養育費の案を作られました」 |
| **OFF に戻す** | **取り下げ**（無かったことにはならない） | **「取り下げられました」** |

- **★ ON は状態変化であると同時に「届く出来事」でなければならない。**
  誰にも届かない状態変化は、存在しないのと同じ
- OFF に戻すことは**できる。**ただし**取り下げとして相手に見える**

### 3.3 文言

```
まだお相手には見えていません。

［ お相手に見ていただく ］

お渡ししたあとで取り下げることもできますが、
一度ご覧になったことは取り消せません。
```

## 4. 状態の作り直し

| 旧（`design.md` §3.2） | 新 |
| --- | --- |
| 未入力 | **未入力** |
| こちらの記録 | **下書き**（自分だけ） |
| お相手のご意向待ち | **お相手のご返事待ち**（渡してある） |
| **内容が異なる** | **お相手から別の案が出ています**（★発生頻度が下がる） |
| 合意済 | **合意済** |
| — | **取り下げました**（新） |

### 4.1 「別の案」が出る場合

了承しない選択はある。そのとき相手は**自分の案を作れる**。
このときだけ2つの案が並ぶ。**ただしこれは例外的な経路になる。**

- 並べるのは「双方の確定した立場」ではなく「**案と、それへの返事**」
- 相手の自然な行動は**了承**であって、対案ではない

---

## 5. ★ 形が3つとも同じになる

| | 形 |
| --- | --- |
| 取り決めを作る | 案を出す → 了承する |
| **変更の申し出（K-6）** | 案を出す → 了承する |
| **準備モード（v2 B）** | 相手が未参加＝**共有 OFF の下書き**。特別扱いが要らなくなる |

**3つが1つの形になる。**実装も画面も減る。

## 6. 受け入れ条件の差し替え

| | 旧 | 新 |
| --- | --- | --- |
| **AC-7** | 片方が入力しただけでは合意にならない | **維持**（了承が第2の行為） |
| **AC-13** | — | **既定では相手に見えない。**渡す操作をして初めて見える |
| **AC-14** | — | **取り下げられる。ただし取り下げたことは相手に見える** |
| **AC-15** | — | 渡したとき、**相手に届く**（状態変化だけで終わらせない） |

---

## 7. 実装への影響

| | |
| --- | --- |
| `Proposal` | `sharedAt` / `withdrawnAt` を持つ |
| 相手側の取得 | **`sharedAt` が無い提案を返さない**（★サーバ側で落とす。画面で隠さない） |
| `consentStateOf` | 「下書き」「取り下げ」を足す |
| `payloadsAgree` | **残す。**別案の経路が残るため。ただし通常経路では自明に真 |
| 了承 | 相手の提案を**そのまま**承諾する（自分の payload を作らない） |

> ★ **サーバ側で落とすこと。**画面で隠す実装にすると、API を直接見れば読める。
> C1（原文が渡らない）と同じ強さで守る。

## 8. 公正証書そのものを預かること（→ 今回はスコープ外）

> 最終的に**公正証書の正式な PDF・画像をアップできる形**にするのが良い。

### 8.1 方向は正しい

いまアプリにあるのは**原案**でしかない。
本物が入ると、取り決め画面が**正典の置き場所**になる。意味が変わる。

### 8.2 ★ 守るべき線

| | |
| --- | --- |
| **中身を読まない** | OCR で項目を抽出したら、**今回やめた「AI が取り決めを作る」に逆戻り**する。**保管するだけ** |
| **食い違ったら PDF が正** | アプリ側の表示は「原案」と書き続ける |
| **保存の扱いが重い** | 本籍・住所・氏名が載る。署名付き URL と有効期限、ケース所属の検査（A-1 / INV-1） |

### 8.3 判断

**今回は実装しない。**Cloud Storage・署名 URL・権限が要り、締切まで2日でデモの中心にならない。

- Issue #6（画像の添付）に**公正証書の PDF として追記する**
- ★ **置き場所はデザインに入れておく。**
  あとから足すと取り決め画面を作り直すことになる
