# 第1部　取次ぎの抽出を直す

## 1. 確定した3つの欠陥

実測（同じ入力を3回・LLM を実際に呼んだ）。

| # | 欠陥 | 実測 |
| --- | --- | --- |
| **A** | **金額が正しく出ない** | 原文「6万円」→ `5000` / `50000` / `50000`。**3回とも誤り** |
| **B** | **スキーマの `title` と `description` が、値として出力される** | `subject:"何について"`（title そのもの）／`shareText:"例: 半分ずつ / 6対4"`（description そのもの）／`subject:"入学金"`（例文） |
| **C** | ★**情報共有が「決まったこと」に行を立てる** | 運動会の写真 → `{"subject":"入学金"}` → 控えとして残る |

**C は今回（T1）の退行である。**
`appendProposal` を外したとき、**ADJUSTMENT と NOTIFICATION の区別まで一緒に落とした。**

```diff
- if (negotiable && requiresAgreement(topic) && relay.payload) { appendProposal(...) }
- else if (!negotiable && relay.payload && threadId) { appendAdjustment(...) }
+ if (relay.payload && input.threadId) { appendAdjustment(...) }   // ★NOTIFICATION も入る
```

設計書には「帰結を kind で分ける」と書いてあった。**FORMAL を消すつもりで、3分岐を1つにしてしまった。**

## 2. ★ 直し方の考え方

締切ではなく、**中身で決める。**

### 2.1 なぜ「抽出をやめる」では駄目か

先に「構造化抽出をやめ、伝聞文だけ残す」を推した。**取り下げる。**

`payload` は2つを支えている。

| | |
| --- | --- |
| `appendAdjustment` | 「決まったこと」の**今回だけの変更** |
| `arrangementFrom` | **約束**（日付＋ラベル）。「8月22日 送迎」 |

やめると、**「決まったこと」タブの中身がほぼ消える。**
壊れているのは抽出であって、抽出という考えではない。

### 2.2 ★ 対になる2つの検査

このアプリには既に、逐語一致の検査がある。**逆向きに使う。**

| | 対象 | 求めるもの |
| --- | --- | --- |
| **既存（INV-4a）** | `content`（伝聞文） | **逐語であってはならない。**原文が流出する |
| **★新規** | `payload`（事実の断片） | **逐語でなければならない。**でなければ捏造である |

> ## 言葉は渡さない。事実は、原文のまま。

この1文で両方が説明できる。

### 2.3 具体

**① 逐語であるべき項目は、原文に含まれることを検査する**

`subject` / `shareText` / `date` / 金額の文字列は、すべて「書かれたとおりに」取るもの。
**原文に部分文字列として現れなければ捨てる。**

これで実測の誤りが**すべて落ちる**：

```
"入学金"            → 原文に無い       → 捨てる
"何について"        → 原文に無い       → 捨てる
"例: 半分ずつ / 6対4" → 原文に無い      → 捨てる
"2023-10-10"        → 原文に無い       → 捨てる
```

**② 金額を LLM に計算させない**

`amountYen: integer`（LLM が「6万円→60000」を計算する）をやめる。

```
amountText: string   … 原文のまま「6万円」
        ↓ ★コードで解釈する。決定的
amountYen            … 60000。解釈できなければ持たない
```

★ これは `formatValue` や `toIncomeBand` と同じ思想である。
**変換できないものは null にして、無かったことにする。**

**③ スキーマから例文を消す**

`description` の「例: 入学金 / 塾の費用」が、そのまま複製されていた。
**例を書かない。**「原文にある語をそのまま」とだけ書く。

★ ①があれば例文が漏れても落ちる。**②③は①の補助**であって、①が本体。

**④ kind の分岐を戻す**

```
FORMAL       → 取次ぎのみ（★取り決めは作らない。今回の方針）
ADJUSTMENT   → 取次ぎ ＋ Adjustment
NOTIFICATION → 取次ぎのみ
```

# 第2部　シナリオとトピックを作り直す

## 3. ★ 重心が、実態と逆になっている

| | 実データ | いまのシナリオ |
| --- | --- | --- |
| 事務連絡・情報共有 | **8割以上** | NOTIFICATION **3 / 19** |
| 合意が要る相談 | 数十件規模 | ADJUSTMENT **14 / 19** |

**交渉を中心に作ってあるが、実際の大半は連絡である。**

## 4. ★ FORMAL シナリオは、行き先を失っている

| | |
| --- | --- |
| `sc_001` 養育費を**決める** | |
| `sc_006` 面会のルールを**決める** | |

**対話からは取り決めを作らないと決めた。**
このシナリオを選んでも、**何も取り決めにならない。**
題が「決める」なのに、決まらない。**果たせない約束になっている。**

### 4.1 ★★ 合意はする。作る場所が変わっただけである

**「決めるシナリオをやめる」＝「合意をやめる」ではない。**

```
取り決め画面   仮案を作る → お相手にお渡しする → 了承 → ★合意成立 → 公正証書の原案
相談（対話）   受け止め → 取次ぎ → 「決まったこと」に控え（個別の相談のみ）
```

| | 合意になるか | 公正証書 |
| --- | --- | --- |
| **取り決め画面** | **なる** | **載る** |
| 相談（対話） | ならない | 載らない |

### 4.2 ★ だが、いま「決める場所」への導線が無い

実装を確認したところ、**2つとも欠けていた。**

| | |
| --- | --- |
| `NOT_NEGOTIABLE_NOTE`<br>「このご相談では、いまの取り決めは変わりません。取り決めを変えるときは、取り決めの画面から申し出ます。」 | **定義されているが、一度も表示されていない** |
| 相談画面 → 取り決め画面のリンク | **無い**（逆向き「このことを相談する」だけある） |

> ★ このまま FORMAL シナリオを外すと、
> **「決める」と書かれた入口が消えるだけで、決める場所には行けない。**

### 4.3 だから、外すのではなく「置き換える」

FORMAL シナリオを消した跡に、**取り決め画面への導線を置く。**

**① 相談の一覧（カテゴリを選ぶ画面）に、1行**

```
──────────────────────────────
取り決めを決める・変える              ▸
養育費・面会交流・財産分与・年金分割
```

**② 個別の相談を開いたときに、`NOT_NEGOTIABLE_NOTE` を出す**

これは**既に書いてある文言**である。表示していないだけだった。

> このご相談では、いまの取り決めは変わりません。
> 取り決めを変えるときは、取り決めの画面から申し出ます。

★ 個別の相談で話がまとまったあと、**取り決めにしたくなる**ことがある。
そのときに**行き先が見えている**必要がある。

「日常の連絡」と「進路・生活」に割れていて、**どちらから入ればよいか決まらなかった。**

### 6.1 「学校でのできごと」と書く理由

実データの大項目6は「学校トラブル・問題行動」である。
**その語を画面に出さない。**

> 喫煙・対人トラブル・脱走。**いちばん言い出しにくい話題**である。
> 入口に「問題行動」と書いてあれば、**書く前に責められた気持ちになる。**

## 7. ★ 緊急・安全確認は、スコープ外とする（決定）

実データには、**警察に捜索願を出す直前**まで発展した家出がある。
体調急変、安否確認（電話が繋がらない）もある。

**このアプリでは扱わない。**

### 7.1 理由

いまのアプリは、真逆を明記している。

> お急ぎいただくご連絡はしません。期限もありません。

**平時の設計としては正しい。**急かさないことを機能にした。
緊急を扱うには、この前提を崩すことになる。

そして**中途半端に扱うと、届かなかったときの責任が重い。**

### 7.2 ★ だから、何も足さない

先に「お急ぎのとき」という出口の画面を提案した。**取り下げる。**
**スコープ外と決めたものに、画面を作るのは矛盾である。**

**既にあるもので足りている。**

| | |
| --- | --- |
| 常設の窓口（第2弾 G・案2） | **相談画面（＝書く場所）に常設**されている |
| 児童相談所虐待対応ダイヤル `189` | **既に一覧にある**（`sr_189`・検証済み） |

> ★ 窓口は**検知に一切反応しない**設計である（監視感を作らないため）。
> 緊急のときにも、**同じ場所に、同じように在る。**

### 7.3 残る判断（データ1行）

常設の窓口の一覧に、**急な体調のための番号**（`#8000` こども医療でんわ相談）を
足すかどうか。

- 足す … 一覧を完成させるだけ。**機能ではない**
- 足さない … 医療は扱わないという線を、そのまま保つ

★ **どちらでも筋は通る。**決めていただく。

## 9. ★ 特別費用のルールは、「決まったこと」に置く（取り決めにしない）

> 「メガネ、キャンプ、医療費、学用品など**1万円超は折半**」

**実データで最も頻出する対立要因**であり、そのご家庭は
**都度の交渉ではなくルールを先に決めていた。**

★ **決めておけば、都度の交渉そのものが要らなくなる。**

### 9.1 公正証書には入れない（判断）

当初は `ps_child_support_v1` の `specialExpenses` を使って**条項にする**案だった。
**やめた。**

| | |
| --- | --- |
| 条項にすると | 変えるのに**相手の同意という重い手続き**が要る |
| このルールは | 暮らしに合わせて**何度でも直すもの** |

> ★ **重くすると、直されなくなる。**

**当事者が自分で決めて、自分で直す。**取り決め（公正証書）とは別の器に置く。

### 9.2 ただし、片方だけでは決まらない

「決まったこと」という題である以上、
**一方が書いただけのものが決まったこととして並ぶのは誤りである。**

取り決めほど重くはしないが、**相手の了承は要る。**
合意・調整と同じ規律を使う（`ruleStateOf`）。

```
片方が選ぶ  → WAITING（★相手には値を見せない。「ご返事をお待ちしています」だけ）
相手も同じ  → AGREED（おふたりで決めました）
内容が違う  → WAITING のまま
```

### 9.3 選択肢だけにする

**自由記述にしない。**書いた言葉がそのまま相手に渡ることになる（C1）。

| | 選択肢 |
| --- | --- |
| 閾値 | 5,000 / 10,000 / 20,000 / 30,000 円 |
| 分け方 | 半分ずつ / そのつど相談する |

★ **API も、用意した選択肢以外を受け付けない**（テストで固定）。

### 9.4 置き場所

「決まったこと」に**区分を分けて**置く。

```
決まったこと
  お約束                    8月22日 送迎（日付つき・その回だけ）
  ──────────────────────
  おふたりで決めたこと       1件 10,000円 を超える費用は、半分ずつ
                           公正証書には入りません。いつでも決め直せます。
```
