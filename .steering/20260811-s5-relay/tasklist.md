## ★ 実機で3件の問題を検出し、直した

### ① context が要求の言い換えになっていた

```
summary: 予定を日曜日に変えてほしいそうです
context: 来週の日程は日曜日に変更してほしいとのことです   ← 同じ内容
```

**要求の繰り返しは事情ではない。**プロンプトに例示を追加し、
「理由が書かれていなければ空文字」を明示した。

修正後、この入力では **context が空になった**（正しい挙動）。

### ② ★strict モードは全プロパティの required を要求する

`required` を外して送ったところ **400** が返った。

これは P3 と衝突する。「月3万」しか書かれていない入力に対して
支払日や終期まで required にすると、**モデルは値を埋めるしかなくなる。**

**解：全項目を required にしたうえで、型と enum に `null` を許す。**

```
type: "integer"             →  type: ["integer", "null"]
enum: ["LAST_DAY","DAY_5"]  →  enum: ["LAST_DAY","DAY_5", null]
```

> **nullable にすることが P3 の担保そのものである。**

②の 400 が出ている間も、**取次ぎ自体は成立していた。**
`payload: なし` として続行し、文章は検査を通ったまま届いている。

> **落ちたときに何が起きるかを先に決めておいたことが効いた。**

## 設計上の記録

### 検査は実行時の門である

**テストで確かめるだけでは足りない。**
LLM の出力は毎回変わるため、本番の1回1回を検査する。

```
生成 → 検査 → 通れば越える
            ↓ 落ちた
        1回だけ作り直す
            ↓ また落ちた
        ★事情を落として最小形で越える
```

**再生成を繰り返さない。**待たせるうえ、通る保証がない。
**事情が伝わらないことより、原文が越えることのほうが重い。**

### 取次ぎ文は LLM に書かせない

定型の枠に、検査を通った要素だけをはめる。

```
{topicLabel}について、{summary}
背景として、{context}
```

自由に書かせると、そこから原文が滲む経路ができる。

### summary にも同じ検査をかける

context だけを検査して summary を素通しすると、**そこから原文が越える。**
落ちたら「ご相談が来ています。」という最小形にする。

### 受け止め（S4）と取次ぎ（S5）は制約が正反対

| | 読む人 | 感情 |
| --- | --- | --- |
| 受け止め | **本人のみ** | そのまま受け止めてよい |
| 取次ぎ | **相手** | 一切通さない |

この非対称性が、プロンプトを分ける理由である。
